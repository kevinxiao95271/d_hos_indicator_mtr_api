# 大查询自动分片拆解设计

> 配套需求文档:《等级评审系统需求说明 v1.1》
> 关联代码:现有指标计算基于动态 SQL(`${sql}`)直接下发 + 按时间维度循环执行,缺少进度反馈、取消、超时控制。
> 本文描述"自动分片拆解"层如何落地,以解决"SQL 一上来就跑死、卡死、无进度"的体验问题。

---

## 1. 问题背景

需求文档中下列场景都存在**大查询**:

| 场景 | 触发点 | 数据规模特征 |
|---|---|---|
| 指标计算(信息化采集) | 指标配置 → 数据源参数验证 / 指标计算 | 病案主表(含诊断、手术分表)全量扫描,聚合条件复杂 |
| 中间表初始化(第三、四、五章) | 中间表维护中心 → 初始化表 | `INSERT INTO … SELECT FROM` 全量灌数,一次性跑整表 |
| 列规则执行 / 初始化所有列(第三、四、五章) | 中间表维护中心 → 列规则配置 | `UPDATE 中间表 SET … WHERE …`,按列逐个执行,单列可能命中百万行 |
| 专病入组(第三、四、五章) | 专病患者规则字典 → 执行入组 | 从病案主表取数插入专病表,按"主要诊断/手术编码/年龄"多条件过滤 |
| 追溯明细 | 评审指标分析 → 追溯 | 查询存储过程返回明细数据集,展示前还可能有过滤条件 |

> **中间表定位(已对照《广西实施细则(2026年版)》+ 需求说明 §3.6 核实,一句话)**:
> 中间表是**第三、四、五章指标**的物化加速:用疾病/手术编码把病案主表筛成"病种/专业子集"落表,统计变 `SUM(FLAG)`。它不改动指标配置、结果落库、对外接口。
> **第四章(单病种,49病种)天然按病种切分**:每病种 = 一组 ICD-10 诊断编码(部分伴手术编码/年龄)定义的独立人群,病种间互不重叠 → 入组/统计/追溯按病种独立执行,每病种一张专病表(或一张表按病种标识区分)。
> 第二章(不良事件,分母为全手术/全出院)无子集复用特征,不建中间表,直查统计。

当前实现的痛点(以 `IndicatorCalculationServiceImpl` 为例):

1. **一条 SQL 全量执行**:`indicatorItemMapper.executeSingleValueQuery(sql)` 直接把整条聚合 SQL 发给 MySQL,无分片。病案主表几百万行时,单条聚合查询扫完全表,接口长时间无任何返回。
2. **无进度反馈**:批量计算虽然 `splitTimeRanges` 按时间段拆了,但只有"全部算完"才有结果,中途既不知道进行到哪,也无法取消。
3. **无超时与熔断**:连接池 max-active=20,一个大查询占住连接不放,后续请求排队,表现为"整个系统卡死"。
4. **无结果复用**:同一指标同一周期反复计算,每次都全量重扫。

**中间表与分片的关系(定位)**:
- 中间表是**物化加速**:把"编码定义的病案子集"预先落表,统计变 `SUM(FLAG)` 小查询——它从根源上**减少**需要分片的大查询;
- 分片拆解是**兜底执行**:对躲不开的全库大查询(病案主表直查聚合、入组灌数、中间表初始化灌数)拆小执行,避免"一上来跑死、无进度"。
- 两者互补、互不依赖:中间表做得越全,分片触发越少;但无论中间表是否存在,分片框架都能独立工作。
- 中间表**不改动整体框架与对外接口**:指标配置、计算结果落库、指标分析 API 完全不变,只是数据来源从"直查病案主表"换成"查中间表"。
- **第四章按病种切分 = 分片框架最直接的应用**:病种即切片,入组时按病种拆片、统计时按病种并行,进度天然按"第 3/49 个病种"展示,无需额外策略。

## 2. 设计目标

- **分片可执行**:把一个大 SQL/大任务拆成若干小片,每片独立执行、独立记录进度,单片执行时间可控(默认上限如 30s)。
- **进度可见**:每个分片任务有状态机(排队 → 执行中 → 成功/失败/已取消),前端轮询即可展示进度条,不再"卡死无反馈"。
- **可取消可恢复**:任务取消后不再提交新分片;失败分片可单独重试,不重跑已完成分片。
- **不阻塞系统**:单分片持有数据库连接的时间有上限,连接池不被占死。
- **透明接入**:对现有指标计算/中间表/入组逻辑是**包装层**,不要求重写业务 SQL;已能按时间拆段的场景(批量计算)自动识别并复用。

## 3. 总体架构

```
前端(评审指标分析 / 中间表维护中心 / 专病入组)
   │ HTTP 轮询(或 SSE)
   ▼
ShardTaskController
   │  提交分片任务 / 查询进度 / 取消 / 重试
   ▼
ShardTaskService ──────────────► ShardTaskRepository(分片任务元数据,表 shard_task / shard_task_slice)
   │   拆片策略、状态机、进度汇总
   ▼
ShardExecutor(核心)
   ├─ 分片策略(时间片 / 键值片 / 行数片 / 单条不改,四选一)
   ├─ 执行器(异步线程池 + 每片独立 Statement,可取消、可超时)
   └─ 回写(每片完成立即落库更新进度)
```

**核心思路:任务(Task) → 分片(Slice)两级模型。**

- `ShardTask`:一次提交(如"计算指标 X,2026-01 ~ 2026-06")。
- `ShardTaskSlice`:拆分后的最小执行单元(如"计算指标 X,2026-03")。

每个 Slice 独立提交给线程池执行,执行完立刻更新自己的状态,任务进度 = 已完成 Slice 数 / 总 Slice 数。用户看到的是"3/6 片完成",而不是白屏等待。

## 5. 分片策略(核心)

根据业务 SQL 的特征自动选择拆片方式。四种策略按优先级判断:

### 5.1 时间片拆分 `TIME_SLICE`(最常用)

**适用**:SQL 中包含时间参数(`#{startDate}` / `#{endDate}` 或 `@统计时间`),且时间跨度可被业务周期整除。
**做法**:把 `[start, end]` 按 `时间维度(月/季/年)` 切段,每段一条 SQL 执行。现有 `IndicatorCalculationServiceImpl.splitTimeRanges` 已是此逻辑,直接复用并包装进分片框架。
**优点**:切分均匀、语义清晰(每片对应一个统计周期)、结果天然按周期落库。
**限制**:仅对时间过滤型 SQL 有效;对"全表 UPDATE/INSERT"类无效。

### 5.2 键值片拆分 `KEY_SLICE`

**适用**:SQL 以"编码列表"(诊断编码、手术编码、科室)为过滤条件,如入组规则的 `IN (...)`、`LIKE 'XX%'`。
**做法**:把编码列表按每片 N 个(默认 500)拆成多片,每片一个 `IN` 子句。例如 2000 个 ICD 编码 → 4 片,每片 `WHERE 主要诊断 IN (500 个编码)`。
**优点**:每片 SQL 体积小(避免超长 IN 列表),命中索引,单片快。
**限制**:需要能定位到编码列表参数;列表需要从配置中解析出来。

### 5.3 行数片拆分 `ROW_SLICE`(兜底,针对 UPDATE/INSERT)

**适用**:无法按时间/键值拆分的大 `UPDATE` / `INSERT … SELECT`,如中间表列规则、初始化表。
**做法**:
1. 先执行 `SELECT COUNT(*) / MAX(id) / MIN(id)` 评估目标行数;
2. 按主键范围(或 `LIMIT chunk` 循环)切成多片,如 `UPDATE t SET flag=1 WHERE id BETWEEN ? AND ?`。
3. 每片批量为一个事务,片内失败不影响其他片(失败策略映射需求中的 STOP / CONTINUE)。

**实现注意**:对 `UPDATE … WHERE 业务条件` 的 SQL,拆片时**自动包裹主键谓词**:`UPDATE t SET … WHERE (业务条件) AND id BETWEEN ? AND ?`。前提是目标表存在数值型主键或单调列,通过元数据探测自动确认,探测失败则退回 5.4。
**优点**:兜底覆盖所有"一条 SQL 打全表"的场景,单片执行时间可控。
**限制**:改造 SQL 有侵入性,需解析或包裹;对无主键/无单调列的表不适用。

### 5.4 单条不改 `NO_SHARD`(明确不拆)

**适用**:
- 查询本身已很小(预估影响行数 < 阈值,如 1 万行);
- 有 `GROUP BY` 聚合、必须在数据库端一次完成(拆开会破坏语义,如科室下钻 `GROUP BY B16`);
- 需求文档中"存储过程"调用(存储过程内部逻辑无法拆),如追溯、微服务绑定过程。

**做法**:不拆,但纳入同一套任务/进度/超时框架,至少保证"超时可断、状态可见",不会无声卡死。

### 5.5 策略选择优先级

```
有存储过程调用? ─────────────────────────────► NO_SHARD(仅超时+进度)
有时间参数且可整除? ─────────────────────────► TIME_SLICE
有编码/科室列表参数? ────────────────────────► KEY_SLICE
目标为 UPDATE/INSERT 且表有主键? ────────────► ROW_SLICE
其余 ───────────────────────────────────────► NO_SHARD
```

策略判定在 `ShardStrategyResolver` 中完成:解析 SQL 文本(占位符、`UPDATE/INSERT` 关键字)+ 查询表元数据(是否有主键、行数预估)+ 读取业务配置(时间维度、编码列表),组合出最终策略。判定结果记录在 `shard_task.shard_strategy`,便于复盘。

## 6. 执行器设计

### 6.1 异步执行

- 使用独立的 `ThreadPoolTaskExecutor`(`shard-pool`),不占用 Tomcat 请求线程;请求线程只做"提交 + 轮询进度",长任务不阻塞 HTTP 响应。
- 线程池配置:core=2, max=4, queue=200(可配置)。**池大小刻意小于数据库连接池(max-active=20)**,保证任何时刻被大查询占用的连接有上限。
- 同一任务的 Slice 默认**顺序**执行(保证依赖顺序,如列规则按执行顺序),不同任务可并行。

### 6.2 单片执行(关键:每片一条独立 Statement)

- 每个 Slice 用**独立 Connection + Statement**,禁止复用跨片长事务。
- 设置 `Statement.setQueryTimeout(sliceTimeoutSeconds)`,默认 30s,超时抛异常 → 该片记 FAILED(策略 CONTINUE 时继续下一片,STOP 时中止任务)。
- 片粒度小,所以单 Statement 超时不会把整个任务打成"无进度"。
- 每片结束(成功/失败)立刻 `update` 分片表,并累加任务进度,前端轮询即可看到进度增长。

### 6.3 取消机制

- 取消请求 → 任务状态置 `CANCELING` → 线程池对**未执行**的 PENDING 片置 `CANCELED`(不入队/跳过)→ 正在执行的片靠 `Statement.cancel()` 中断(MySQL 驱动支持)→ 任务终态 `CANCELED`。
- 已完成的片保留结果,不回滚(任务取消 ≠ 数据回滚,已在库中的周期结果有效)。

### 6.4 失败与重试

- 失败策略沿用需求文档的 `STOP` / `CONTINUE`:
  - `STOP`:某片失败 → 任务 `PARTIAL_FAILED`,记录失败片,后续 PENDING 片标 `CANCELED`。
  - `CONTINUE`:失败片记 FAILED,继续下一片,任务终态 `PARTIAL_FAILED`,汇总错误信息。
- 支持"仅重跑失败片":`POST /api/shard-task/{id}/retry-failed`,将 FAILED 片重置为 PENDING 重新入队。
- 自动重试:单片执行失败后按 `maxRetry`(默认 1)自动重试一次,重试仍失败才记 FAILED(避免瞬时抖动)。

## 7. 进度与交互协议

### 7.1 提交

```
POST /api/shard-task
{
  "bizType": "INDICATOR_CALC",
  "bizKey": "metricCode=A01&timeDim=MONTH&start=2026-01&end=2026-06",
  "params": { ...业务参数原样透传... }
}
→ 200 { "taskId": 123, "strategy": "TIME_SLICE", "totalSlices": 6 }
```

同步返回:taskId + 拆分策略 + 总分片数。前端拿到即可渲染"共 6 片"。

### 7.2 进度轮询

```
GET /api/shard-task/{id}
→ { "status": "RUNNING", "totalSlices": 6, "doneSlices": 3,
    "progressPercent": 50.00, "currentSliceNo": 4,
    "slices": [ { "sliceNo": 1, "status": "SUCCESS" }, ... ],
    "errorMsg": null }
```

前端每 2~3s 轮询一次(或改用 SSE 推送)。页面呈现"3/6 · 50% · 正在执行第 4 片",替代白屏等待。可选取消按钮。

> 说明:为控制篇幅,SSE 只作为可选增强;首版用轮询即可满足"有进度"的体验要求。

### 7.3 取消 / 重试

```
POST /api/shard-task/{id}/cancel
POST /api/shard-task/{id}/retry-failed
```

## 8. 与现有代码的对接点

| 现有位置 | 现状 | 接入方式 |
|---|---|---|
| `IndicatorCalculationServiceImpl.calculateIndicator` | 单指标单周期,直连查询 | **不改**。作为"一片"的原子执行体,由分片框架包装:提交任务 → 拆片 → 每片调用它 |
| `batchCalculateIndicators` | 已有 `splitTimeRanges` 按时间拆段 | **替换/包装**:把"指标 × 时间段"二维矩阵展平为 Slice 列表,交给 `ShardExecutor` 执行,获得进度与取消能力 |
| `calculateDeptDrill` | 内部 `GROUP BY B16` 全量查询 | **不拆**(5.4),但包一层任务状态,保证超时可断、有进度显示(单片) |
| `IndicatorItemMapper.executeDynamicQuery` / `executeSingleValueQuery` | `${sql}` 直发 | **复用**,分片 SQL 仍走这两个 Mapper 执行;新增 `executeUpdate` 支持 UPDATE/INSERT 类 Slice 与行数回传 |
| 中间表初始化 / 列规则(需求 3.2,第三、四、五章指标) | 新模块,尚未在本仓库实现 | 按本文框架实现:初始化表 = ROW_SLICE 或 NO_SHARD;初始化所有列 = 每列一个 Slice(天然按列拆),列规则执行顺序即 slice_no。中间表是"病案主表的编码子集物化",用于加速第三、四、五章指标,**第四章按病种天然切分**(每病种一组编码=一张专病表),不改变指标配置/结果落库/对外接口 |
| 专病入组(需求 3.6.1,第三、四、五章指标) | 新模块 | **第四章按病种切片(首选)**:每个病种一个 Slice,天然互不重叠;其余入组条件含编码列表 → KEY_SLICE;条件为时间/科室 → TIME_SLICE |
| 追溯(需求 3.7.5) | 新模块,存储过程 | NO_SHARD,超时 + 进度 |

**关键原则:分片框架是包装层,不侵入业务 SQL。** 业务侧只提供"给定参数执行一片"的函数,框架负责拆片、调度、进度、取消、重试。

## 9. 关键配置(application.yml 新增)

```yaml
indicator:
  shard:
    enabled: true
    pool:
      core-size: 2
      max-size: 4
      queue-capacity: 200
    slice:
      timeout-seconds: 30        # 单片 SQL 超时

      poll-interval-ms: 2000     # 前端建议轮询间隔(文档用)
```

## 10. 实施步骤(建议顺序)

1. **阶段一(基础框架)**:建 `shard_task` / `shard_task_slice` 表 + 实体 + Mapper;`ShardTaskService` 状态机 + `ShardExecutor` 线程池执行器 + `ShardTaskController`(提交/进度/取消/重试)。此阶段无业务接入,先保证框架自测通过(单测覆盖状态流转、取消、失败重试)。
2. **阶段二(指标计算接入)**:包装 `batchCalculateIndicators`,替换掉裸的 `splitTimeRanges` 循环为分片任务;接入 `calculateIndicator` 为单片原子执行体。对现有 101 条 e2e 用例回归。
3. **阶段三(中间表/列规则/入组接入)**:实现 `ROW_SLICE` 与 `KEY_SLICE`(含 SQL 包裹主键谓词),接入中间表初始化、列规则批量执行、专病入组。此处 SQL 解析工作量大,建议单独迭代并配行数验证。
4. **阶段四(追溯/存储过程接入)**:`NO_SHARD` 超时 + 进度包裹,接入追溯明细。
5. **阶段五(体验增强)**:SSE 推送、历史任务查询页、失败片可视化重试。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 拆片改变 SQL 语义(尤其聚合/去重) | 只对明确可拆的 SQL 拆片;`GROUP BY` 聚合与存储过程一律 NO_SHARD;拆片前后结果一致性用行数/值对拍验证(测试脚本比对全量结果 = 分片汇总结果) |
| `ROW_SLICE` 包裹 `UPDATE` 改变执行计划 | 片内事务,片间独立;对拍验证更新行数之和 = 全量更新行数 |
| 超长 `IN` 列表 | KEY_SLICE 默认 500/片,单条 SQL 体积受控 |
| 线程池/连接池耗尽 | 线程池 max < 连接池 max-active;单 Statement 超时兜底 |
| 拆片任务与原有同步接口并存 | 保留原同步接口,分片作为"批量/大任务"入口,按 bizKey + 阈值判断是否走分片(预估行数 > no-shard-max-rows 才分片) |
| 进程重启丢任务 | 元数据落库,启动时把 RUNNING 任务重置为 PENDING(或标记 INTERRUPTED),支持恢复 |

## 12. 效果指标(验收口径)

- 单个大查询(原全量执行)拆片后,**单片执行时间 ≤ 30s**(超时即失败重试/中止),不再出现"连接占死、页面无响应"。
- 批量计算任务从提交起**1s 内返回 taskId**,进度可轮询,取消在下一个切片边界生效(正在执行的片最迟 30s 内被中断)。
- 分片汇总结果与全量执行结果**逐项对拍一致**(针对 TIME_SLICE / KEY_SLICE 场景)。
- 对现有 101 条 e2e 用例无回归(阶段二验收)。

## 13. 附录:单片执行伪代码(取消 + 超时)

```java
// ShardExecutor 单片执行核心逻辑
public SliceResult executeSlice(ShardTaskSlice slice) {
    try (Connection conn = dataSource.getConnection();
         Statement stmt = conn.createStatement()) {
        stmt.setQueryTimeout(config.getSliceTimeoutSeconds());   // 单片超时
        boolean ok = stmt.execute(slice.getSql());
        // 成功 → 更新分片状态 SUCCESS,累加任务进度,回写结果摘要
        slice.markSuccess(collectSummary(stmt));
    } catch (SQLTimeoutException e) {
        slice.markFailed("单片执行超时(" + config.getSliceTimeoutSeconds() + "s): " + e.getMessage());
    } catch (Exception e) {
        slice.markFailed(e.getMessage());
    }
    return slice.getResult();
}

// 取消:任务状态置 CANCELING → PENDING 片跳过 → 执行中片由 Statement.cancel() 中断
```
